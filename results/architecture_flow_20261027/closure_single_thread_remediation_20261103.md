# 单线程约束补救评估

## 已确认事实

登记协议要求每进程一个线程；历史 P1 进程实际出现额外线程和非主线程 CPU 活动。该约束在已执行的整组实验上不能追认通过。证据见 `p1_thread_envelope_review_20261031.json`。

P1 构建的 CMake 缓存中 `VPR_EXECUTION_ENGINE=serial`，但 `TATUM_EXECUTION_ENGINE=auto`；构建定义包含 `TATUM_USE_TBB`。VPR 的全局 TBB 限制在该构建的条件编译路径中未启用。当前证据不定位线程创建的具体调用栈，不能断言仅修改某一选项就已解决问题。

源码 `vendor/beyond-flatland-src/libs/EXTERNAL/libtatum/CMakeLists.txt` 列出 Tatum 的 `serial` 引擎，`libtatum/CMakeLists.txt` 对该选项有明确分支。一个可检验的候选是使用独立构建目录，将 VPR 和 Tatum 引擎都设为 `serial`；这会产生新二进制，需要重新绑定哈希和实验协议，不能替换已归档程序或将新结果混入原运行。

CPU 亲和性限制到一个核心只能限制可运行 CPU，不保证进程不存在多个线程，不能独自证明满足每进程单线程约束。也不能把三次不重叠的运行等同于线程受限或独占主机。

## 验证所需步骤

1. 保留原二进制、输入及实验记录；使用隔离构建目录和单独名称构建候选，记录完整构建命令、依赖、编译宏、源与二进制哈希。
2. 用登记前的小规模代表性输入执行候选布局、时序和路由；从进程启动到结束采样线程数与非主线程 CPU 活动，并检查其他依赖是否创建线程。瞬时单次采样只能提供有限证据。
3. 检查候选与原构建的打包语义、布局合法性、固定输入路由、VPR FULL 及独立审计。单线程构建可能改变浮点时序、布局或运行结果，必须报告差异。
4. 如需严格满足原协议并据此支持完整范围结论，须在新登记方案下重新执行受影响的实验，重新开展同样的成功/失败、配对、统计和完整性审计；小样本验证或口头披露不能修复历史运行的约束违例。重跑的具体范围应依据各流程实际线程行为及预先冻结的审计标准确定。

以上步骤列出补救所需证据；后续候选验证及其限制见下文，尚未证明约束已满足。

## 后续候选与线程诊断

串行 Tatum 候选已经独立构建。spmv/SB 布局 VPR 采样线程峰值为 1，打包语义与布局坐标和原运行一致；官方 A0 在此布局上通过 FULL 及限定范围独立路由审计。该样本不能证明所有流程符合约束。

在 spmv/Hybrid-O 的进程树采样中，OpenROAD 峰值为 28 个线程；单独运行分区的另一项诊断峰值为 29 个线程，采样期间 215 个不同线程身份出现 CPU 时间增长。线程创建拦截的四个调用栈中，第一个来自初始化 `drt::TritonRoute` 时构造的 Boost.Asio 线程池；后面三个来自 `par::KWayFMRefine::InitializeGainBucketsKWay` 分区细化路径中的 `std::thread`。因此 VPR/Tatum 串行构建与 OpenROAD `-threads 1` 不足以保证分区全程每进程单线程。拦截诊断会改变运行时序，不用于计时或性能推断；调用栈不证明已覆盖全部创建路径。

原独立采样、调用栈、配置和命令保存在 `single_thread_candidate_20261103/`。该结果推翻了仅修改 Tatum 引擎就能完成补救的假设；对 TritonPart 的实际线程实现也必须采取可验证措施。

## 固定版本源码核查

本地 OpenROAD 包报告 `2.0-17598-ga008522d8`。已下载版本号对应的官方提交 `a008522d88b669ac4c985609533cf5a3d2649222` 的相关源码和哈希到 `single_thread_candidate_20261103/openroad_source_excerpt/`。版本字符串与源码提交对应，但尚未证明本地包是由该源码逐位可复现构建。

该版本的 `KWayFMRefine.cpp` 在初始化增益桶、更新增益桶和删除堆元素时显式创建 `std::thread`；`Multilevel.cpp` 也为多个候选解的细化显式创建线程。所检查代码中的这些创建不受 `OMP_NUM_THREADS` 直接控制，且运行证据显示 `-threads 1` 仍发生线程创建。它们与调用栈一致，但此检查不是整个源码树中线程创建位置的穷举。

可靠的候选需要获取并固定完整 OpenROAD 源码及其依赖，检查所有线程创建路径，设计显式的串行实现并以新二进制开展受控验证。直接限制 CPU 亲和性、拦截线程创建使其失败，或将 OpenMP 环境变量视为全部线程的限制，都不能证明约束满足。修改分区执行顺序可能改变结果，须保留旧结果并重新验证。

## 路由程序线程诊断

`single_thread_candidate_20261103/route_thread_diagnostics_20261103/` 对同一固定输入的原始 A0、R1 和 B2 分别做了 `pthread_create` 拦截和线程轮询；三次均成功，观察峰值依次为 21、21 和 19 个线程。每组最先记录的调用栈经由 oneTBB `global_control` 的销毁路径。该诊断会扰动执行时序，不证明这些线程同时计算、各阶段 CPU 使用或性能影响；它表明严格的每进程单线程问题不能只局限于 P1 布局。A0、R1、B2 对应构建缓存均为 Tatum 和 VPR 引擎 `auto`。如需实现严格约束，应分别固定并验证三个路由程序的串行构建，重新登记受影响的训练、测试与计时；旧程序、旧结果和原选参过程需保留，不能把新二进制直接称为原始官方程序。
